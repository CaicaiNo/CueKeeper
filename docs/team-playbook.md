# 团队与派工手册

这份文档是团队协作规则的完整版，按需阅读。每次 agent run 只注入工作区上下文里的精简摘要；
角色细节、项目事实、产物与缓存规范都在这里查。

坐标：`docs/team-playbook.md`（仓库 CueKeeper）。修改规则时先改本文，再同步工作区上下文摘要。

## 1. 派工模式：父 issue + 阶段化 sub-issue

- 一个需求一个父 issue，描述写清目标、输入、产出物、验收标准、边界。
- 有依赖的拆分用 stage 表达顺序：
  - 第 1 阶段：`--stage 1 --status todo`，立即开跑；
  - 后续阶段：`--stage 2..N --status backlog`，等上一阶段 barrier 关闭后，由父 issue 的 assignee 逐级 promote 成 `todo`。
- 创建子任务带 `--project <id>`，不要落到默认项目。
- **一次只放一条链**：前一条链进入 `in_review` / `done` 再放下一阶段，除非两条链完全不共享文件。
- 开工前查重：`multica issue runs <issue-id> --active --siblings`。同一家族已有在跑的 run，不重复派发。
- 建完统一核对：`multica issue children <parent-id>`，确认没有漏 stage、没有误把整个链建成 `todo`。

## 2. 长 run 的上限与回收

平台对本地 runtime 没有单 run 超时配置，必须人工设上限：

- 派发时在描述里写明「预计 N 分钟，超过 2N 分钟按失败处理」。
- 超过阈值先核实：`multica issue runs <issue-id> --active --output json`，看 `started_at` 与最新输出。
- 确认无进展再取消：`multica issue cancel-task <run-id> --issue <issue-id>`，然后 `multica issue rerun-task <run-id>` 或重新派。
- 默认红线：单 run 超过 45 分钟仍未交付，视为卡死；先保存它最后的输出再取消。
- 不要用 sleep / 轮询等它结束。需要等外部结果时用条件唤醒：
  - `multica issue wakeup create <issue> --until-issue <other-id> --until-issue-state done`
  - `--until-status in_review`、`--until-pr merged`、`--until-pr checks`、`--until-children-done`

## 3. 运行中补充信息：优先 steer

目标 agent 正在跑时，新评论只会在它结束后才被读到，等于多跑一轮完整上下文。

- 纠偏、补事实、收窄范围时用：
  - `multica issue comment add <issue> --parent <trigger-comment> --content-file ./note.md --steer <run-id>`
  - 或 `--steer-active`（送进该 issue 上所有正在跑、且允许补充的 run）
- 每个 run 最多 3 条 steer，全部 agent 合计 10 条；超出会退回普通触发路径。
- steer 只用于「改变当前正在做的事」。新任务、收尾回复走正常路径。
- 查可 steer 的 run：`multica issue runs <issue-id> --active --output json`，看 `can_supplement`。

## 4. 上下文纪律

- 读评论分两步：先 `--roots-only --summary --compact` 扫线程，再 `--thread <id> --tail 30` 展开需要的那条。不要整段拉。
- 长文档放仓库 `docs/`，需要时再读；不要塞进 issue 描述或评论。
- 交付评论只写：做了什么、关键输出 / 验证数字、遗留项。不复述过程。
- 同一 issue 连续微调时，先在本地把改动做完再回报，减少 run 次数。

## 5. 交付与状态

- 交付即评论；没有交付评论不得置 `in_review`。
- 阻塞时写 `blocked`，说明缺什么、需要谁做什么。
- 关闭 issue 会连带禁用它的 wakeup；重开不会恢复，需要重新建。

## 工作流程

1. **Mika** 接需求 → 判断是否为团队任务 → 建 issue **指派给「游戏开发团队」**，写清目标、输入、产出物、验收标准、边界。
2. **Codex（队长）** 接单 → 拆子任务 → 按矩阵指派（`todo` 直接开跑，有依赖用 `backlog`）。
3. 执行者在自己的任务评论里写**交付总结**。
4. **Codex** 复核会进 main 的代码与设计，给出「通过 / 需修改 + 依据」。
5. **Mika** 汇总结果转达成员，维护任务板状态。

**归属规则**：游戏开发任务默认指派给团队，不直接指派个人。例外只有两类：① 明确的收尾 / 复核动作；② 成员点名要某个智能体做。

**交付即评论**：任何任务结束前必须在自己的任务里写一条交付评论（做了什么、验证数字、遗留项）。没有交付评论一律视为未完成，状态不得写 `in_review`。

## 测试规范

- 每条测试必须断言**可观察的真实行为**（真实输入、真实结算、真实 UI 变化）。只断言构造成功、返回值非空、退出码为 0 的测试视为无意义。
- 不允许「0 个用例 + exit 0」当作通过；不许为了证明完成新建演示脚手架。
- 优先覆盖核心规则与端到端链路；数量不是目标。
- 允许删减只用于打印 / 截图 / 自证且没有断言的验证代码，需在交付里列明删了什么。

## 容量策略

- 成员要求：Codex 额度在重置前尽量用完，预留 5% 容错。
- 平台与 CLI 不提供额度 / 余额 / 重置时间接口，Mika 无法测量；要按 95% 排期需要成员提供**剩余额度百分比**与**重置时刻**。
- 未拿到数字前：用关键实现与复核把 Codex 填实，不用容易的活凑数。
- Codex 闲置是允许的；不要拿琐碎任务填他的时间。

## 产物交付规范（大文件）

- **超过上传上限的产物不上传、不拆分上传。** 平台单文件上限约 100 MB（实测 205 MB 被拒：`The request is larger than the server accepts`），上传速度约 30 MB/分钟。
- 这类产物**保存在本机固定目录**，回复里给出：绝对路径 + 文件大小 + SHA256 + 一句话说明怎么构建的。
- 本机产物目录惯例：`/Users/sheng/multica-v1-artifacts/<任务号或主题>/`，同目录放 `BUILD-INFO.txt` 与 `SHA256SUMS.txt`。
- 只有用户**明确要求**时才拆分上传（`split` + `cat` 重组），并在回复里写清分片顺序和校验值。
- 交付措辞要明确「文件在本机，未上传」，不要让用户以为已在附件里。

## 本机操作边界

- 任何会改动系统的动作（`installer`、`launchctl bootstrap/bootout`、钥匙串信任证书、写 `/usr/local` 或 `/opt`）**必须先征得用户同意**再执行。
- 沙箱验证只用临时目录（`MULTICA_V1_ROOT=/tmp/...`）+ 临时 label，测完立即卸载并核对：无残留进程、无残留 plist、无安装收据、钥匙串无新增证书。
- 不在用户现有部署上做覆盖式试验；产物先在沙箱跑通再交付。

## 本 Mac 平台/自建服务任务的分工（2026-11-26 修订）

- **方案评估、可行性分析、规格与决策备忘录 → Code-leader 本人做**，不要派给 mac-codex。
- **mac-codex 只负责复核**：对会进 main 的代码、或高风险改动，给出「通过 / 需修改 + 依据」。不承担调研、方案设计、可行性评估。
- 实现 → OpenCode；本机环境、打包与一次性系统操作 → Qoder；资料调研与整理 → CodeBuddy DS4.1。
- 不要把"评估一下 X 可行吗"这类任务丢给审核者；审核者只在有具体产出（代码/设计文档/备忘录）之后介入。

## 缓存与产物目录规范（2026-11-26 修订 v2）

**目的**：只有最终交付物长期保存，中间产物允许被系统清掉；清理只由用户决定。

- **构建与临时产物**：写系统临时目录（`/tmp`，优先 `mktemp -d` 或 `/tmp/multica-<任务号>`）。任务结束**必须自行清理**。
- **可重建的中间产物**（依赖缓存、构建缓存、下载包、日志、截图草稿）：`~/Library/Caches/multica/{build,runs,logs,downloads}`。放这里就是接受**可能被系统清理**，不得当作唯一副本。
- **最终交付产物**：唯一允许放在 `~` 根目录的成果目录是 `~/multica-v1-artifacts/<任务号或主题>/`，同目录放 `BUILD-INFO.txt` 与 `SHA256SUMS.txt`。只有「要交给用户、要长期保留」的成果才进这里，中间产物不得混入。
- **不要在 `~` 根目录新建其他目录**；除 `~/multica-v1-artifacts` 外没有例外。
- **超过上传上限的文件**：留在本机交付目录，回复里给绝对路径 + 大小 + SHA256，并说明「未上传」。
- **谁创建谁清理**：任务结束时删除自己本次产生的临时目录与中间产物，不清理别人的目录。
- **删除必须经用户确认**：任何删除动作（`rm`、批量清理脚本、`--apply`）都要先给出清单与回收量，等用户明确同意后再执行。禁止对真实目录做无人确认的批量删除；dry-run 之外一律先问。
- **永不删除**：`resources/` 下的 PSD、`~/Documents/git/` 里用户的 checkout、`~/multica-v1-artifacts/` 的交付物、未推送的分支、正在运行任务的目录（含 `.task_lock`）。
- **保留期只是参考**：任务目录 7 天、中间产物 14 天、日志 7 天、下载缓存每组件留最新 1–2 个版本。到期不等于自动删，仍需用户确认。
