# 录制 / 回放一致性审计

本单只做离线审计：读 `src/`、`native/`、`test/` 与既有文档，给出「录到的」和「回放时实际做的」之间的差异、静默错配风险和检测方案。**没有启动 GUI、没有录制、没有回放，也没有改 `src/`。**

一句话结论：**不能保证完全一致。** 当前能证明的是「动作被驱动按某条路径投递了」，不能证明「用户当时做的和回放做的事产生了同一个结果」。下文把能证明的、不能证明的、以及现在会「报告通过但做错」的路径全部列出来。

## 1. 为什么不可能完全一致

录制不是原始输入回放，而是一次有损编译：物理事件 → 猜测用户意图 → flow 里的元素/键/文本。回放再用另一条路径（可访问性动作、批量文本、物理按键、绝对坐标）把意图重新表达。两次表达之间至少有四层不可逆：

1. **语义层**：点击被编译成「对元素执行默认动作」，不是「在同一像素按下再抬起」。双击、拖拽、修饰键点击、press-and-hold 都在这一层被折叠或丢弃（`native/recording-pointer.swift:120-147`、`src/record.ts:67-78`）。
2. **文本层**：按键被编译成一段 `type` 文本，不再逐键投递，也不记录输入法、选区、光标位置和撤销栈（`native/recorder.swift:362-384`、`src/record.ts:87-104`、`src/desktop.ts:296`）。
3. **定位层**：元素被编译成 `role` + `name` + 可选 `path`/`index`，回放要求精确匹配（`src/locator.ts:107-139`）。树里同形元素、动态名称、行序变化都可能让同一条 locator 换一个目标，或被判为 `NOT_FOUND`。
4. **环境层**：窗口位置、显示器缩放、剪贴板、输入法状态、应用数据、网络与动画都不在 flow 里。回放只绑定应用路径/窗口 ID/标题，不绑定这些（`src/app-identity.ts:466-481`、`docs/architecture.md:27`）。窗口标题还是每次快照的精确匹配条件（`src/locator.ts:87-89`）：保存/另存为改了标题，后续快照会 `WINDOW_MISMATCH`。这类失败是响亮的，但前面的动作已经产生了副作用。

因此正确的目标不是「完全一致」，而是：

- **能不一致时大声失败**（定位失败、窗口变化、投递未确认）；
- **能做到一致的部分用断言证明**，而不是用动作 `passed` 自证；
- **明知表达不了的操作，在录制时就标记出来**，不要留到最后才发现。

## 2. 判定口径

矩阵里的「失败响度」分四级：

| 级别 | 含义 | 用户看到什么 |
| --- | --- | --- |
| L0 静默 | 不进 flow，也没有 warning | 没有任何提示，后续步骤照常执行 |
| L1 警告 | 事件被跳过，CLI 带 `warnings`，退出码通常仍为 0 | 终端/JSON 里一条 warning，容易被忽略 |
| L2 部分录制 | 已写 flow，但带 `partial: true`，退出码 1 | 知道不完整，但已录部分仍会被使用 |
| L3 硬失败 | 该动作或整个流程失败，不假装成功 | 报告 `failed` / `blocked`，后续停止 |

「可能成功但做错」指：动作和流程都报 `passed`，但应用实际状态与录制时不一致。**这类问题只有断言能发现**，见第 5 节。

## 4. 静默错配清单（按风险排序）

排序依据：发生概率 × 用户是否会误以为通过。同一项同时列出现有缓解，避免把「已经拦住」的情况当成新问题。

### R1 · IME / 中文被录成拼音

- **触发**：中文输入法组字时录入，例如输入 `nihao` 后选「你好」。
- **用户可见后果**：flow 里出现 `type "nihao"`，回放把拼音写进目标字段；报告 `passed`。若上屏用了 return/space，还会多出一次可能在错误控件上执行的按键。
- **为什么现在是静默**：拼音字母落在 `32..126`，通过 ASCII 过滤，没有 warning（`native/recorder.swift:377-378`）。
- **现有缓解**：无。只有直接输入非 ASCII 字符时才报 `UNSUPPORTED_TEXT`（`native/recorder.swift:382`）。
- **检测**：录制时检测输入法组字状态（TIS 输入源类型 `kTISPropertyInputSourceType`，或 AX 焦点控件的组字/选中态）。最省事的做法是「检测到就拒绝并标记」，见 6.0。

### R2 · 剪贴板内容不随流程走

- **触发**：任何 Cmd+C / Cmd+X / Cmd+V 流程。
- **用户可见后果**：回放机器的剪贴板是别的文本/图片/空，粘贴结果不同；流程通过。
- **现有缓解**：无。`key` 动作只带键名和修饰键（`src/contracts.ts:181-188`），报告里也没有剪贴板字段。
- **检测**：录制时对 `meta+c` / `meta+v` 标记 `CLIPBOARD_DEPENDENT`；回放后必须用 `assert` 校验目标值或截图，见 5.3。

### R3 · `type` 是批量写入，不是逐键输入

- **触发**：所有文本输入；在实时校验、自动补全、输入掩码、字符计数、按键监听或撤销粒度敏感的应用里最明显。
- **用户可见后果**：同样的文本进了字段，但应用行为不同（不触发补全、不报校验、撤销一次退回整段）；目标已有内容时，插入还是替换由驱动/控件决定，录制时的光标位置不再有效。
- **现有缓解**：只保证「驱动没报未投递」；`delivery` 为 `delivered_verified` / `delivered_unverified` 都算通过（`src/desktop.ts:170-178`）。`delivered_unverified` 的语义由上游定义，本项目不读回（`docs/windows.md:102`）。
- **检测**：录制时记录文本输入前的值长度/摘要（不记内容），回放后读值比对；或者在 flow 里强制 `type` 后接 `assert`，见 5.3。

### R4 · 坐标点击是绝对坐标，只做包含校验

- **触发**：canvas/自绘区域、窗口被移动或缩放、换显示器、副屏在左/上。
- **用户可见后果**：点还在窗口里，但落在另一个控件/空白/错误像素；报告通过。
- **现有缓解**：`--headed`、聚焦窗口、重新快照、`contains(bounds, point)`（`src/desktop.ts:284-294`）。这只证明「点在窗口内」，不证明「点到了同一元素」。
- **检测**：录制时同时保存窗口相对坐标和该点的命中节点签名；回放前 dry-run 重算，见 5.2。路径固定流程已经直接拒绝坐标点击（`src/record.ts:75`、`src/run.ts:546`），可作为默认策略。

### R5 · 拖拽完全丢失

- **触发**：滑杆、文本选区、列表排序、拖放上传、窗口移动/缩放。
- **用户可见后果**：状态停在拖动前；后续步骤基于错误状态执行，可能仍通过。
- **现有缓解**：`DRAG_SKIPPED` warning（L1），退出码 0；只有「整场没有任何可支持动作」时才 `EMPTY_RECORDING`。
- **检测**：录制时把 `DRAG_SKIPPED` 升级为流程级 `fragile` 标记；回放前 `flow doctor` 必须提示。见 6.2。

### R6 · 双击 / 三击折叠成单击

- **触发**：选词替换、Finder 重命名、表格单元格编辑、展开节点。
- **用户可见后果**：一次点击把光标放到某处，随后 `type` 插入而不是替换；文件名编辑可能变成定位而不是全选。
- **现有缓解**：`MULTI_CLICK_COLLAPSED`（L1），退出码 0（`test/recording-pointer-tests.swift:77-79`）。
- **检测**：矩阵已有的 `clickState` 信息足以在录制时直接标记；新增连击语义见 6.1。

### R7 · 滚轮丢失导致后续定位漂移

- **触发**：列表/表格需要滚动才能看到目标；画布视口；懒加载。
- **用户可见后果**：回放时列表停在顶部，按 `index` 解析到另一行；或者元素根本不在树里，报 `NOT_FOUND`（这时是响亮的，但已经晚了）。
- **现有缓解**：`UNSUPPORTED_EVENT`（L1），按 code 去重，长会话只出现一次。
- **检测**：录制时记录滚动次数/方向，至少能在 flow 中留下 `fragile` 标记；新增滚动动作见 6.3。

### R8 · 同一应用内换窗口，键击串窗或丢失

- **触发**：多文档窗口、主窗口 + 检查器面板 + 新建窗口。
- **用户可见后果**：两种坏结果：找不到焦点控件 → 文本段被 `UNSAFE_TEXT_TARGET` 丢掉（L1）；原窗口控件仍带 `focused` 标志 → 文本被记到原窗口的控件上（L0），回放把内容打进错误的窗口。
- **现有缓解**：点击其他窗口会 `boundary`；键盘只校验前台**应用**，不校验窗口（`native/recorder.swift:345-348`）；`FOCUS_CHANGED` 只在应用切换时出现（`native/recorder.swift:192-207`），应用内换窗没有任何提示。
- **检测**：录制时每次文本/键事件都校验「事件目标 PID + 前台窗口是否仍是绑定窗口」，而不是只校验 PID。这是低成本、高收益的加固点。

### R9 · 菜单与系统对话框整段缺失

- **触发**：用菜单打开功能、保存/打开面板、权限确认、覆盖确认。
- **用户可见后果**：flow 缺少关键步骤；回放时对话框再次出现，后续动作打在面板后面；由于可访问性快照不看遮挡，报告仍可能 `passed`，但文件没有保存。
- **现有缓解**：`boundary` 静默（`src/record.ts:267-274`）；键盘因目标 PID 不符被静默丢弃（`native/recorder.swift:343-348`）。
- **检测**：录制时把「目标窗口之外出现系统面板」当成可记录的事件（至少发 warning），而不是 `boundary`；回放前 `flow doctor` 对含 `meta+s`/`meta+o` 等保存/打开快捷键的流程提示「可能依赖对话框」。

### R10 · locator 漂移：同名换人

- **触发**：列表插入/删除行导致 `index` 移位；名称含计数、日期、URL、文件路径；应用升级改变角色树深度；语言切换。
- **用户可见后果**：三种情况：
  1. 匹配不到 → `NOT_FOUND`，L3，响亮但已经执行了前面的步骤；
  2. 匹配多个 → `AMBIGUOUS`，L3；
  3. **仍匹配一个但换了元素 → L0，回放点到/输入到另一个对象。**
- **现有缓解**：精确匹配 + 歧义报错（`src/locator.ts:107-125`）；`--dry-run` 只验证当前状态能解析（`src/run.ts:534-559`、`src/assertion.ts:342-363`），**不比较录制时的身份**。
- **检测**：录制时保存 locator 的「身份签名」（角色、名称、路径、序号、窗口内归一化几何）；回放前逐条对比。这是 5.1/5.2 的核心。

### R11 · 非文本控件上的可打印键被丢掉

- **触发**：空格切换勾选/按钮、单键快捷键（`j`/`k`/`r`）、游戏或画布输入。
- **用户可见后果**：这些键在原生层被当成 `text` 发出，CLI 找不到唯一可编辑焦点控件，报 `UNSAFE_TEXT_TARGET` 并丢掉；退出码 0。
- **现有缓解**：只有 warning；没有「把可打印字符回退成 `key`」的策略（`src/record.ts:87-96`）。
- **检测**：录制时如果文本事件发生在非文本焦点上，改记 `key` 而不是丢弃；这需要扩展 `key` 的可表示字符集合（当前 schema 只允许字母数字与命名键，`src/contracts.ts:184`）。

### R12 · 修饰键点击、右键、中键整类缺失

- **触发**：多选、加选、上下文菜单、中键粘贴/新标签。
- **用户可见后果**：选择状态不同，后续批量操作只作用于一部分；右键流程整段丢失。
- **现有缓解**：`UNSUPPORTED_CLICK` / `UNSUPPORTED_EVENT`（L1）。
- **检测**：录制时统计被跳过的点击占比；超过阈值时拒绝产出「看似完整」的 flow，而不是只给警告。

### R13 · 悬停完全不可见

- **触发**：tooltip、悬停展开菜单、悬停才出现的按钮/把手。
- **用户可见后果**：回放里这些元素不存在或不可点击；若回放仍能通过 locator 点到，可能触发的是另一个状态。
- **现有缓解**：无（未订阅 `mouseMoved`）。
- **检测**：录制时若点击命中节点的 `visible` 在当时依赖悬停，离线无法判断；只能靠录制后人工检查或断言。

### R14 · 激活首击被当成内容点击重放

- **触发**：录制第一个动作是点击一个非前台窗口/标签页来激活它。
- **用户可见后果**：回放时目标已经在前台，同一次点击会作用到真实控件（切换标签、触发按钮），而不是只激活窗口。
- **现有缓解**：录制会保留这次点击（`scope: activation` 仍然 `accepted`，`test/recording-pointer-tests.swift:17`）；没有「仅激活」的标记。
- **检测**：录制时知道 `targetAppFrontmost == false`，可以标记该点击为 `activation-only`，由回放决定是否跳过。当前 flow 没有这个字段。

## 5. 一致性检测方案

目标不是再写一个「动作执行器」，而是把「录制时的身份」和「回放时的现实」放在一起比较，并在不一致时拒绝。

### 5.1 录制时：每个动作即时定位校验 + 稳定性标记

现状：

- 文本段已经有再解析：`resolve(snapshot, locator)`（`src/record.ts:96-97`）。
- 点击**没有**再解析：`toLocator` 之后直接入 flow（`src/record.ts:76-77`）。
- 没有记录命中数、备选、几何或名称是否易变。

建议（不改变 flow v1，产物放旁车文件）：

1. 每个动作完成后，用**同一份已抓取的快照**再解析一次 locator，确认恰好 1 个命中；不额外抓树，避免打破 1200 ms 快照预算和 2000 ms `STALE_CAPTURE`（`src/record.ts:288-293`）。
2. 记录一份 `fidelity` 旁车（示例见 `design/fidelity/fidelity-sidecar.sample.json`）：
   - `resolution.matchCount`、是否需要 `path`、是否需要 `index`；
   - `identity`：角色、名称、角色路径、同名序号；
   - `geometry`：元素 bounds 与窗口相对中心；**不改窗口绝对坐标**，避免跨机无意义；
   - `evidence`：点击点是否命中该节点、文本目标是否可编辑、是否处于焦点；
   - `stability` + `reasons`。
3. 稳定性规则（离线可判定，不猜）：

   | 判定 | 条件 |
   | --- | --- |
   | `unstable` | 同一 locator 在当前树命中 0 或多个且无法用现有 `index` 唯一定位；或元素 bounds 缺失 |
   | `fragile` | 依赖 `index`；或依赖长度大于 5 的角色路径；名称含数字/日期/URL/文件名/百分比；或命中节点的面积超过窗口 50%（容器/根节点）；或文本目标没有 `focused`/不可编辑；或该动作是 `point` |
   | `stable` | 唯一命中、名称固定、无需 `index`、几何正常、证据齐全 |

4. 对点击额外做「点命中回验」：`hitTest(snapshot, point)` 的结果必须与写入的 locator 指向同一节点；否则标 `fragile`（`src/locator.ts:146-155`）。这一步纯内存，不增加系统调用。

旁车文件不进入 flow，因此旧回放器不需要认识它；`flowSha256` 绑定原 flow，防止改 flow 后拿错旁车（`src/flow.ts:99-101`）。

### 5.2 回放前：dry-run 全量定位 + 与录制时身份对比

现状：`run --dry-run` 会逐条解析 locator、预检断言与基线（`src/run.ts:483-485,515-519,537,550,556`），但只看「现在能不能解析」，不看「解析到的还是不是同一个东西」。

建议新增一个可选的对比阶段（离线也能用 `--snapshot`）：

| 对比项 | 通过 | 漂移（drifted） | 阻塞（blocked） |
| --- | --- | --- | --- |
| 命中数 | 1 | — | 0 或多，且无法用原 `index` 唯一定位 |
| 身份签名 | 角色/名称/路径/序号一致 | 仅序号或几何变化 | 角色/名称/路径变化导致指向不同节点 |
| 坐标点 | 窗口相对坐标对应的命中节点签名一致 | 相对坐标偏移超过基线窗口尺寸的 2%，或命中节点变化 | 点不在窗口内 |
| 文本目标 | 可编辑、唯一、焦点可达 | 当前值长度与录制时不同 | 元素不存在或不可编辑 |

输出建议（`design/fidelity/flow-doctor.sample.json` 是示例）：

- `status: fail` 当任一动作 `blocked`，退出码 1；
- `status: warn` 当仅 `drifted` 或 `fragile`，退出码 0，但在报告中保留；
- 逐条给出录制值、当前值、差异原因，便于人工判断。

注意：dry-run 不点击、不聚焦，所以它无法证明「回放时焦点会落在同一控件」。这部分只能靠回放后断言。

### 5.3 回放后：断言最终状态，而不是动作状态

报告里的 `passed` 只表示动作被投递（`src/desktop.ts:170-178`、`src/run.ts:558-559`），不表示结果正确。可用的真实观测已经存在：

- 元素 `text`/`value`/`exists`/`visible`（`src/assertion.ts:148-188`）；
- 窗口 `title`/`exists`（`src/assertion.ts:303-321`）；
- 区域截图像素对比（`src/assertion.ts:239-300`）。

建议的硬规则（先作为 `flow doctor` 的检查项，不强制改运行器）：

1. 每个 `type` 之后至少一条 `assert value/text`；
2. 每个改变数据的 `click` 之后至少一条可观察断言（元素/窗口/截图任选）；
3. 使用 `meta+v` 的流程，必须在粘贴后断言目标值；
4. 使用 `point` 的流程，必须至少一条截图断言，且 `region` 覆盖点击区域；
5. 截图断言必须设 `maxDiffRatio`（0 只适合完全静态的窗口）。

这些规则能把 R1–R10 从「静默」降级为「失败」。代价是作者要多写断言；收益是把「动作执行成功」和「结果正确」分开。

### 5.4 `flow doctor` 与报告字段的取舍

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| 新增 `cuekeeper flow doctor <flow>`，读旁车 + 可选 `--snapshot` | 不改 flow/report schema；可离线；能在录制完立刻跑；能拦截 R1–R12 的已知模式 | 看不到回放时的实时漂移；需要旁车文件 | **第一阶段采用**。先做静态检查（无断言、point、剪贴板键、连击/拖拽警告、locator 依赖 index/path），再做可选的快照对比 |
| 在 `report.entries` 加 `fidelity` 字段 | 每次回放都留下证据；工作台和查看器可直接展示 | `reportSchema` 是 `additionalProperties: false`（`src/contracts.ts:352-358`），旧版读取新报告会直接 schema 失败；要么升 report 版本并写迁移，要么让旧读取器容忍未知字段 | **延后**。先以旁车 `report.fidelity.json` 形式随报告目录保存（首版不打包进 ZIP，`report pack` 需要单独扩展），等报告 v2 再正式纳入 |
| 把 `fidelity` 塞进 `entry.message` | 零 schema 改动 | 非结构化，无法稳定解析；污染人类可读信息 | **不采用** |

推荐路径：**旁车 + `flow doctor`（无 schema 变更）→ 报告目录旁车 → 未来 report v2 再结构化**。这样不会让当前所有已发布报告和读取器失效。

## 6. 优先级：先补哪三个操作

排序原则：先补「现在会被静默做错」且「录制侧已经拿得到原始证据」的操作。下面三项都满足：原生层已经观察到了事件，只是被丢弃。

### 6.0 先做零成本护栏（在新增操作之前）

这些不需要新动作，只需要在录制/检查阶段标记，能立即降低 R1/R2/R4 的风险：

| 护栏 | 行为 | 验收 |
| --- | --- | --- |
| IME 检测 | 组字状态或非 ASCII 上屏时，拒绝把拼音串写入 flow，报 `IME_TEXT_UNSUPPORTED` | 用拼音录「你好」，flow 中不出现 `nihao`；CLI 退出码非 0 或流程标记 `fragile` |
| 剪贴板标记 | `meta+c/x/v` 动作标 `CLIPBOARD_DEPENDENT`；`flow doctor` 要求后续断言 | 含粘贴的流程在 doctor 中至少一条 `warn` |
| 坐标点击身份校验 | 录制时保存窗口相对坐标 + 命中节点签名；回放前对比 | 窗口平移 40 px 后 doctor 报 `drifted` |

### 6.1 第一优先：双击 / 三击

- **为什么先做**：`clickState` 已经在事件里（`native/recorder.swift:416-418`），不增加权限或新事件源；当前是「有 warning 但照常通过」，用户最容易忽略。
- **契约改动**：`click` 增加可选 `count: 1|2|3`（默认 1）。旧 flow 不受影响；旧读取器会因为 `additionalProperties: false` 拒绝新 flow，需要按 flow 版本策略处理（见风险）。
- **回放**：驱动当前只有单次 `click(ref)`（`src/desktop.ts:283`），需要驱动支持连击，或在 Cuekeeper 侧增加物理连击（`CGEventPost` 两次 down/up，`clickState` 递增）。物理连击必须要求 `--headed`。
- **验收（可观察行为）**：
  - TextEdit 中双击单词后输入新词，磁盘内容等于「新词」而不是「原词+新词」；
  - Finder 中双击文件名进入全选编辑态（或等价的可观察状态）；
  - 三击选中整段后替换，结果等于新段。
- **风险**：不同应用的连击间隔/距离判定不同（系统默认 500 ms、数像素），录制时的双击在回放时可能被识别成两次单击；必须用系统阈值而不是硬编码。只做「录制到 clickState=2/3」不够，回放要真的产生连击。

### 6.2 第二优先：拖拽

- **为什么**：`leftMouseDragged` 已经在监听集合里（`native/recorder.swift:565`），起止点都可拿到；拖拽是当前影响面最大的「整类操作消失」。
- **契约改动**：新增 `kind: "drag"`，字段 `from`/`to`（元素 locator 或 point）与可选 `durationMs`。这是 flow v1 的动作联合扩展，旧读取器同样需要版本策略。
- **回放**：现有 `Desktop` 接口没有拖拽方法（`src/desktop.ts:17-35` 只有 click/clickPoint/type/press；驱动是否另有命令，本项目未使用）。需要在 Cuekeeper 侧增加物理拖拽（`CGEventPost` 的 down → 多次 dragged → up），并要求 `--headed`、窗口已聚焦、起止点都在窗口内；不能走可访问性默认动作。
- **验收**：
  - 滑杆从 20% 拖到 80%，读回值/截图符合；
  - 文本编辑器中从字符 A 拖到字符 B，选中文本等于区间内容；
  - 列表拖拽排序后，第一项的名称等于拖入项。
- **风险**：物理拖拽受窗口遮挡、显示器缩放、系统拖拽阈值影响；拖拽过程中目标窗口失焦会中断；拖动窗口标题栏会移动窗口本身，必须区分「移动窗口」和「内容拖拽」。首版建议只支持内容区拖拽，标题栏拖拽继续 L1 警告。

### 6.3 第三优先：滚轮

- **为什么**：`scrollWheel` 已经在监听集合里（`native/recorder.swift:565`），且滚动缺失会让后续 `index` 定位静默漂移（R7），属于「一个缺失动作污染后面所有步骤」。
- **契约改动**：新增 `kind: "scroll"`，字段 `target`（元素或窗口）、`deltaX`/`deltaY`（逻辑点或行数）、可选 `anchor`（滚动后用于稳定定位的元素）。
- **回放**：`Desktop` 接口没有滚动方法（`src/desktop.ts:17-35`），需要在 Cuekeeper 侧合成 `CGEvent(scrollWheelEvent2Source:…)`；滚动后必须重新抓树并确认 `anchor` 可见，否则报 `SCROLL_INCOMPLETE`，不要继续点击。
- **验收**：
  - 长列表中滚动 5 行后点击第 6 行，点击的是第 6 行的内容；
  - 画布滚动后，坐标点击命中录制时同一元素（用截图断言验证）；
  - 滚动到顶部/底部时，后续动作不会越界。
- **风险**：触控板惯性滚动（momentum）无法精确复现；行高不固定时「滚 5 行」不等于固定像素；`scrollWheel` 的 delta 单位在触控板和鼠标上不同。首版建议记录并回放**像素级 delta**，并用 `anchor` 定位而不是假设行数。

### 为什么不先做右键、悬停、多窗口

- 右键的上下文菜单在 macOS 上是独立窗口，录制需要跨窗口绑定，属于架构级改动；在没有菜单动作契约前，先保持 L1 警告更安全。
- 悬停需要持续监听 `mouseMoved`，事件量可能是点击的几十倍，会直接冲击 1000 事件上限和快照预算。
- 多窗口需要把「一个 flow 一个窗口」扩展成「窗口集合 + 切换动作」，会动到 `app-identity` 和 `run.bindWindow` 的核心契约，风险远高于前三个。

## 7. 离线测试计划

所有用例都不接触桌面。纯 dry-run 用例用 `--snapshot`；需要执行动作并读回状态的用例，用 `test/` 里已有的测试替身（`test/cuekeeper.test.mjs:35-45` 的 `fakeDesktop`，或录制协议桩 `recordFixture`），不使用真实驱动。测试必须断言可观察结果（flow 内容、报告状态、元素命中、断言结果），不能只断言退出码。

| 编号 | 用例 | 夹具 | 断言（真实行为） | 覆盖 |
| --- | --- | --- | --- | --- |
| T1 | 列表插入行导致 `index` 漂移 | 录制快照 A：3 行，点击第 2 行；回放快照 B：顶部插入 1 行 | 当前实现：同一条 locator 解析到 B 的第 1 行（证明静默错配）；目标实现：doctor 报 `LOCATOR_DRIFT` 并阻塞 | R10、5.2 |
| T2 | 角色树加一层包装 | 快照 B 在原路径中插入 `group` | `run --dry-run` 报 `NOT_FOUND`，流程 `blocked`，证明这类漂移是响亮的 | R10、5.2 |

## 8. 明确不承诺的边界

- **游戏、远程桌面、受保护/DRM 内容**：这些界面通常没有可访问性树，或明确禁止合成输入；本方案不覆盖。
- **安全输入**：只要系统处于 secure input，录制会拒绝（`src/record.ts:62-65,73`）；这是有意为之，不是缺陷。
- **canvas/自绘界面**：没有可访问性节点时只能坐标点击，且无法验证「点到了什么」；只保证不越界，不保证语义。
- **跨机器/跨显示器一致性**：窗口位置、缩放、DPI、字体渲染、输入法、剪贴板都不在 flow 里；同一台机器的同一布局是前提。
- **时序与动画**：`wait`/`assert` 只能轮询属性，不保证动画结束；需要作者写稳定的等待条件。
- **非确定性数据**：时间、随机数、网络内容、登录态变化不在 flow 里；截图断言对这类变化天然敏感。
- **驱动器自身语义**：`delivered_verified` / `delivered_unverified` 的具体验证范围由 agent-desktop 1.3.1 定义（`src/desktop.ts:38,170-178`）。本项目只把它当作「投递状态」，不当作「应用结果」。

## 9. 结论

- 当前能端到端工作的范围：**单次左键单击、ASCII 文本、命名特殊键、常用快捷键**，且需满足单窗口、无修饰键、元素有稳定名称等前提；其余 14 类操作要么不录，要么只录到一部分。
- 真正危险的不是「不支持」，而是 **R1–R10** 这类「有 warning 但退出码 0」或「完全静默」的路径；其中最容易被误认为通过的是 IME、剪贴板、批量文本和坐标点击。
- 检测的正确层次是：**录制时标身份 → 回放前比身份 → 回放后断言结果**。三件都不做，只看 `report.status === "passed"`，就无法回答「录到的和做的到底一样不一样」。
- 推荐先落 6.0 的零成本护栏，再按 6.1–6.3 补双击、拖拽、滚轮；契约与报告的正式扩展留到 report v2 / flow 版本升级时统一处理。
